# 形式驗證與等效性檢查

## 什麼是形式驗證

形式驗證（Formal Verification）是一套利用數學方法證明數位電路設計符合其規格的技術。與傳統的動態模擬不同——後者僅測試有限的輸入向量組合——形式驗證透過嚴謹的邏輯推理，為設計的正確性提供數學保證。

形式驗證的核心思想是將設計與規格轉化為數學命題，然後用自動化工具證明（或反駁）這些命題。如果證明成功，則該設計在所有可能的輸入序列與狀態組合下都滿足規格。這消除了模擬覆蓋率不足所帶來的風險。

形式驗證在現代半導體設計流程中已成為不可或缺的環節，特別是在安全關鍵應用（汽車、醫療、航太）與高可靠性設計（伺服器、網路處理器）中。

## 形式驗證的類型

### 模型檢查（Model Checking）

模型檢查是一種自動化技術，透過窮舉搜索設計的所有可達狀態來驗證性質。給定一個有限狀態機模型與一個用時序邏輯表述的性質，模型檢查器會遍歷所有狀態空間，確認該性質是否在所有路徑上都成立。

**基本原理**：

1. 將硬體設計抽象為有限狀態機（FSM）
2. 將規格轉化為時序邏輯公式（如 LTL、CTL、Property Specification Language）
3. 演算法搜索狀態空間，確認性質是否在所有可能的路徑上成立
4. 如果發現違反，產生反例軌跡（counterexample trace）用於除錯

**狀態爆炸問題（State Explosion）**：模型檢查面臨的最大挑戰是狀態爆炸——設計的狀態數隨狀態元件（正反器）數量呈指數成長。一個具有 n 個正反器的電路最多有 2ⁿ 個狀態。當 n 超過幾百時，直接的狀態列舉變得不可行。這促使了多種緩解技術的發展。

### 等效性檢查（Equivalence Checking）

等效性檢查是形式驗證中最廣泛使用的技術之一。它的目標是證明兩個電路表示的輸入/輸出行為完全相同。這在設計流程中的多個階段都至關重要：

- **RTL 與合成後網路表**之間：確認邏輯合成沒有引入錯誤
- **工程變更（ECO）前後**：確認局部修改沒有改變整體功能
- **不同抽象層級之間**：確認行為級、RTL 級、閘級描述的一致性
- **掃描鏈插入前後**：確認 DFT 修改沒有影響功能性

**組合等效性檢查（Combinational EC）**：比較兩個純組合電路（無記憶元件）的布林函數。基本方法是從輸入到輸出建構一塊電路（miter），將兩個電路的對應輸出用 XOR 連接，然後檢查是否存在任何輸入組合使 XOR 輸出為 1（表示不一致）。這個問題可以化為 SAT 問題求解。

**序向等效性檢查（Sequential EC）**：考慮含有狀態元件的電路。這比組合等效性檢查更複雜，因為兩個電路可能具有不同的狀態編碼、不同的管線深度、或經過了暫存器重新排列（retiming）。現代的序向等效性檢查器使用多種技術：狀態映射（state mapping）、不變量推導（invariant derivation）、以及符號模擬（symbolic simulation）。

**流程整合**：典型的等效性檢查流程如下：

1. RTL 設計作為黃金參考（golden reference）
2. 邏輯合成產生最佳化網路表（implementation）
3. 設定對應點（compare points）：通常是所有主要輸出與正反器輸入
4. 等效性檢查工具自動證明或反駁對應點的等值
5. 如果失敗，產生除錯資訊協助定位不一致的邏輯閘

### 定理證明（Theorem Proving）

定理證明使用互動式證明助理來建立設計正確性的形式化證明。與自動化的模型檢查和等效性檢查不同，定理證明需要使用者的專業知識來引導證明過程。

**常用工具**：

- **ACL2**（A Computational Logic for Applicative Common Lisp）：廣泛用於處理器、算術單元、快取一致性協定的證明
- **Coq**：基於依賴型別（dependent type）的證明助理，支援高階邏輯
- **Isabelle/HOL**：高階邏輯定理證明器
- **Lean**：微軟研究院開發的互動式定理證明器，在數學形式化領域日益流行

定理證明的優勢在於其表達能力——可以處理無限狀態系統與高階屬性——但代價是需要大量的人工投入。在硬體驗證中，定理證明通常用於證明關鍵的微架構屬性或算術單元的正確性。

### 形式屬性檢查（Formal Property Checking）

形式屬性檢查將 SystemVerilog Assertions（SVA）與形式驗證引擎結合。設計者用 SVA 撰寫設計應滿足的屬性（assertions）、環境假設（assumptions）、以及需要覆蓋的行為（cover properties），然後形式工具自動證明這些屬性。

**SVA 基礎**：

```systemverilog
// 序列：當 req 為高時，下一個時脈週期 gnt 必須為高
property req_gnt;
  @(posedge clk) req |=> ##[1:3] gnt;
endproperty

assert property (req_gnt) else $error("Request not granted in time");

// 假設：輸入 req 不能持續為高超過 10 個週期
assume property (@(posedge clk) $rose(req) |-> ##[1:10] $fell(req));

// 覆蓋屬性：確認 full 訊號在模擬中被觸發
cover property (@(posedge clk) $rose(full));
```

形式屬性檢查工具會針對每個 assert 屬性進行證明：試圖在設計狀態空間中尋找違反屬性的路徑。如果所有路徑都滿足屬性，該屬性被標記為 proven；如果發現違反路徑，工具產生波形顯示具體的錯誤情境。

## 模型檢查的演算法

### BDD 為基礎的方法

二元決策圖（Binary Decision Diagram, BDD）由 Randal Bryant 在 1986 年提出，為布林函數提供了一種正規化（canonical）表示法。BDD 的特性使得兩個布林函數的等價性可以在常數時間內判斷，因為等價的函數必然具有完全相同的 BDD 結構。

BDD 在模型檢查中的應用：

1. 將電路的狀態轉移關係表示為 BDD
2. 將要驗證的性質也表示為 BDD
3. 透過 BDD 上的操作計算所有滿足性質的可達狀態集合
4. 如果所有初始狀態的可達狀態都滿足性質，則性質成立

BDD 的問題在於節點數量可能在最壞情況下指數成長。某些電路（如乘法器）的 BDD 會爆炸到無法實用的程度。這促使了 SAT 為基礎的方法的發展。

### SAT 為基礎的方法：有界模型檢查（BMC）

有界模型檢查（Bounded Model Checking, BMC）由 Biere 等人於 1999 年提出，使用 SAT 求解器代替 BDD。BMC 的核心思想是：將電路的 k 步展開（unrolling）轉化為 SAT 問題，檢查是否存在長度為 k 的違反路徑。

對於一個性質 P，BMC 嘗試尋找使 `¬P` 在 k 步之內成立的可滿足賦值。如果 SAT 求解器回報不可滿足（UNSAT），則在 k 步內沒有錯誤。透過逐步增加 k 值，可以在理論上找到任何有限長度的錯誤。

BMC 的優勢在於：

- SAT 求解器通常比 BDD 更能處理大規模電路
- 可以輕鬆處理超過 1000 個正反器的設計
- 若發現錯誤，SAT 求解器直接產生反例向量，可直接用於模擬除錯

侷限在於：

- BMC 只能證明在有限步數內無錯誤，無法證明無限時間域的正確性
- 對於需要大量週期才能觸發的錯誤，BMC 可能效率低下

### IC3 / PDR

IC3（Incremental Construction of Inductive Clauses for Indubitable Correctness）由 Aaron Bradley 在 2011 年提出，也稱為 PDR（Property Directed Reachability），是當前最先進的模型檢查演算法。

IC3 的核心思想是歸納不變量（inductive invariant）。它不直接計算可達狀態集合，而是透過逐步推導出一個歸納不變量來證明性質：

1. 從初始狀態開始，建立一個漸進的近似可達狀態框架
2. 使用 SAT 求解器檢查是否存在從框架某層到違反狀態的轉移
3. 如果發現，嘗試推導一個歸納子句（inductive clause）來排除該路徑
4. 重複這個過程，直到框架足夠強以證明性質，或發現真正的違反路徑

IC3/PDR 的優點：

- 不需要 BDD 的節點爆炸問題
- 不需要 BMC 那樣依賴於固定的展開深度
- 通常能證明深度極大的性質
- 產生的歸納不變量可以幫助理解設計行為

## 等效性檢查的實務

### 組合等效性檢查流程

現代等效性檢查工具的操作流程相當自動化：

1. **讀取設計**：讀入黃金參考（通常是 RTL）與實作（通常是合成後閘級網路表）
2. **對應點匹配**：自動識別兩個設計間的對應點（主要輸出、掃描正反器、鎖存器）
3. **邏輯錐提取**：對每個對應點，提取其輸入端的邏輯錐（fan-in cone）
4. **布林比對**：對每個邏輯錐對，建構 miter 電路，並用 BDD 或 SAT 求解
5. **結果報告**：標示所有等價點與不等價點

### 序向等效性檢查的挑戰

當兩個電路的狀態編碼或管線結構不同時，組合等效性檢查無法直接應用。序向等效性檢查需要額外的步驟：

- **狀態映射**：識別兩個電路中功能對應的正反器
- **暫存器重新排列**（retiming）處理：合成器可能移動暫存器位置以最佳化時序
- **管線差異**：行為級與 RTL 級之間可能有不同的管線階段數
- **狀態編碼差異**：有限狀態機在不同實現中使用不同的狀態編碼方式

### 業界工具

**Synopsys Formality**：業界最廣泛使用的等效性檢查工具。支援從 RTL 到閘級、閘級到閘級的完整流程。能夠處理先進製程（3nm/5nm）的複雜設計，整合 Synopsys Design Compiler 流程。

**Cadence Conformal**：Cadence 的等效性檢查解決方案，以強大的除錯功能聞名。支援 ECO 分析與自動修復建議。可以與 Cadence Genus 與 Innovus 流程緊密整合。

**OneSpin**（Siemens EDA）：專注於正式屬性檢查與等效性檢查，在安全關鍵應用領域有廣泛使用。

## 開源形式驗證：SymbiYosys

SymbiYosys（sby）是目前最主要的開源形式驗證框架。它提供了一個前端介面，將 Yosys（Verilog 合成器）與多種後端求解器整合在一起。

### 工作流程

使用 SymbiYosys 的基本步驟：

1. 撰寫 `.sby` 組態檔，指定設計檔案、要驗證的屬性、使用的引擎
2. 執行 `sby -f <file>.sby` 啟動驗證
3. SymbiYosys 使用 Yosys 將設計讀入，並與屬性一起編譯成求解器可處理的形式
4. 調用後端求解器進行證明或反駁
5. 生成結果報告與反例波形（可用 GTKWave 檢視）

### .sby 檔案範例

```
[options]
mode prove
depth 50

[engines]
smtbmc z3

[script]
read -formal design.v
prep -top top

[files]
design.v

[verifies]
assert_top
```

### 支援的引擎

SymbiYosys 支援多種驗證引擎：

- **bmc**：有界模型檢查，使用 SAT/SMT 求解器，檢查指定深度內的錯誤
- **prove**：完整證明模式（使用 IC3/PDR 演算法或 BMC 的 k-induction）
- **cover**：覆蓋分析，尋找滿足特定條件的狀態路徑
- **induction**：使用歸納法證明性質

**深度參數（depth）**：對於 bmc 引擎，depth 指定搜尋的最大週期數。對於 prove 引擎，若求解器支援 IC3/PDR，depth 主要作為資源限制。

### 支援的求解器

SymbiYosys 可以搭配多種求解器：

- **Z3**：微軟開發的 SMT 求解器，功能最全面，支援位元向量、陣列、未解釋函數等多種理論
- **Bitwuzla**：專為位元向量與陣列理論最佳化的 SMT 求解器，速度優秀
- **Boolector**：位元向量 SMT 求解器，在硬體驗證領域表現良好
- **SuperProve**：基於 ABC 的 IC3/PDR 引擎，專門為硬體驗證設計
- **Yices**：高效 SMT 求解器，支援多種邏輯理論
- **aiger**：使用 AIG（And-Inverter Graph）格式的 SAT 求解器

### 在開源流程中的角色

SymbiYosys 與 Yosys 的整合為開源 EDA 生態提供了完整的形式驗證能力。在 OpenLANE 流程中，SymbiYosys 可以與其他工具協同：

1. Yosys 進行 RTL 合成與最佳化
2. SymbiYosys 對合成過程中進行等效性檢查
3. 對關鍵控制邏輯進行正式屬性驗證
4. 對 FPGA 設計的位元流進行正確性確認

## SystemVerilog Assertions（SVA）

SVA 是 SystemVerilog 語言中用於描述設計行為與屬性的重要子集。它由兩個主要部分構成：

### 斷言（assert）

斷言是設計必須滿足的屬性。如果斷言被違反，模擬器或形式工具會報告錯誤。

```systemverilog
// 握手協定的斷言：req 有效後，ack 必須在 1 到 5 週期內回覆
property handshake;
  @(posedge clk) $rose(req) |-> ##[1:5] ack;
endproperty
assert property (handshake);
```

### 假設（assume）

假設是對設計輸入環境的約束。在形式驗證中，假設限定了求解器的探索空間——只考慮滿足所有假設的輸入序列。

```systemverilog
// 假設：輸入資料在 valid 有效時必須穩定
assume property (@(posedge clk) valid |=> $stable(data));
```

### 覆蓋（cover）

覆蓋屬性用於記錄設計中的特定行為是否在驗證過程中發生。在形式驗證中，cover 指令引導工具尋找滿足該條件的具體路徑。

```systemverilog
// 覆蓋：FIFO 從空到滿的完整經歷
cover property (@(posedge clk) empty ##[*] full);
```

### 嵌入函數與運算子

SVA 提供豐富的時序運算子與內建函數：

- `##`：時序延遲運算子（`##2` 表示兩個時脈週期後）
- `|->`：蘊含運算子（重疊蘊含）
- `|=>>`：非重疊蘊含
- `##[m:n]`：可變時序範圍
- `[*m:n]`：序列重複
- `$rose(expr)`：表示 expr 在當前週期上升
- `$fell(expr)`：表示 expr 在當前週期下降
- `$stable(expr)`：表示 expr 在當前週期保持不變
- `$past(expr, n)`：表示 n 個週期前的 expr 值

## 形式驗證與模擬的取捨

### 形式驗證的優勢

**窮舉正確性**：形式驗證遍歷所有可能的輸入組合與狀態序列，提供 100% 的覆蓋率保證。這對安全關鍵設計至關重要。

**早期錯誤檢測**：形式驗證可以在設計流程早期（甚至在測試平台完成之前）發現錯誤。錯誤越早發現，修復成本越低。

**反例產生**：當形式驗證發現錯誤時，它自動產生導致錯誤的具體輸入序列，大幅簡化除錯。

**不需要測試平台**：對於屬性檢查，只需要撰寫屬性本身，不需要撰寫完整的測試平台與激勵。

### 形式驗證的弱點

**狀態爆炸**：雖然 IC3/PDR 與 SAT 為基礎的方法大幅緩解了這個問題，但複雜的資料路徑（如大型乘法器、記憶體陣列）仍然會讓形式工具難以處理。

**屬性撰寫難度**：撰寫正確且完整的屬性需要專業知識。如果屬性本身有誤，形式驗證的結果會誤導設計者。

**需要量化時間**：形式驗證工具可能花費大量時間嘗試證明無法證明的屬性。使用者需要設定合理的資源限制（深度、時間、記憶體）。

### 模擬的優勢

**擴展性**：模擬可以處理全晶片包含數十億電晶體的設計，而形式驗證通常只能處理幾千到幾萬個正反器的區塊。

**易於使用**：傳統的測試平台與波形除錯流程已為工程師所熟悉，學習曲線比形式驗證平緩。

**資料路徑驗證**：對於算術運算、資料處理等資料路徑邏輯，模擬可以快速覆蓋大量測試案例。

### 業界最佳實務

在現代設計流程中，形式驗證與模擬並非競爭關係，而是相輔相成：

**形式驗證適用於**：
- 控制邏輯（FSM、仲裁器、握手協定）
- 關鍵安全屬性（相互排除、死鎖避免）
- 管線控制的冒險（hazard）檢查
- 記憶體一致性協定
- 加密引擎的正確性驗證

**模擬適用於**：
- 資料路徑（加法器、乘法器、移位器）
- 全晶片整合驗證
- 效能驗證（吞吐量、延遲）
- 軟硬體協同驗證
- 電源管理序列測試

**混合策略**：
- 用形式驗證證明控制邏輯的正確性
- 用模擬覆蓋資料路徑的大規模測試
- 用等效性檢查確保合成流程中沒有引入錯誤
- 用覆蓋度分析辨識需要更多驗證努力的部分

## 形式驗證與 eda4 的關係

eda4 的 verilog2rust 合成器將 Verilog 程式碼轉換為 Rust HDL 表示。這個轉換過程的正確性至關重要——如果轉換器引入了錯誤，所有依賴其輸出的後續步驟都會受到影響。

形式驗證，特別是等效性檢查，可以在這個流程中發揮關鍵作用：

1. **合成正確性保證**：使用 SymbiYosys 對 verilog2rust 的輸入和輸出進行等效性檢查，確認轉換沒有改變電路功能
2. **與 Yosys 的交叉驗證**：將 verilog2rust 的輸出與 Yosys 合成的結果進行比對，確認兩者功能一致
3. **回歸測試中的形式驗證**：在持續整合流程中加入形式驗證，確保程式碼修改沒有引入功能回歸

此外，對於 FPGA 設計流程，形式驗證可以確保最終的位元流（bitstream）與原始的 RTL 描述一致。這是雙重驗證（double-checking）的實踐——不僅依賴合成與佈局佈線工具的內建檢查，還透過獨立的形式驗證工具進行最終確認。

## FPGA 設計中的形式驗證

形式驗證在 FPGA 設計流程中的應用逐漸普及。與 ASIC 設計類似，FPGA 設計也需要確保從 RTL 到位元流（bitstream）的每一步轉換都是正確的：

**RTL 屬性驗證**：在 FPGA 綜合之前，使用 SymbiYosys 對 RTL 設計中的關鍵控制邏輯進行形式屬性驗證。這可以在綜合與實現（place-and-route）之前就發現設計錯誤。

**綜合後等效性檢查**：FPGA 綜合工具（如 Yosys、Vivado）在將 RTL 映射到 LUT 與 FF 時可能引入錯誤。使用等效性檢查可以確認綜合前後的功能一致性。

**位元流驗證**：雖然位元流層級的等效性檢查在實務上較少執行，但對於安全關鍵的 FPGA 應用（航太、醫療、軍事），可以透過形式驗證確保實現結果與設計意圖完全一致。這通常涉及將位元流反解譯為 LUT 內容與 FF 連接，再與原始 RTL 進行比對。

隨著開源 FPGA 工具鏈（Yosys、nextpnr、SymbiYosys）的成熟，形式驗證正在從 ASIC 領域向 FPGA 領域擴展，為開放式硬體設計提供了更高層次的正確性保證。
